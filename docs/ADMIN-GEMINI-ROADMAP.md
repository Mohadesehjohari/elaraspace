# رودمپ افزودهٔ Elara — پنل مدیر اصلی و مدیریت Gemini

**ثبت درخواست:** ۲۱ سپتامبر ۲۰۲۶؛ **وضعیت: صرفاً برنامه‌ریزی شده و هنوز اجرا/تست نشده است.** این سند مکمل [رودمپ اصلی](PRODUCT-ROADMAP.md) است. هر ایدهٔ تازهٔ آرن در گفت‌وگوی برنامه‌ریزی به رودمپ و Git منتقل شود و در پاسخ لینک تغییر ارائه شود؛ اگر دسترسی Git قطع بود صریحاً اعلام شود. بدون تأیید/تست، موردی را «انجام شده» علامت نزنید.

## ۱. داشبورد مدیر اصلی سایت — Owner Admin

> **Admin Core v0.1 کدنویسی شد:** مسیر `/admin/`، ورود Firebase، بررسی سند نقش `admins/{uid}`، Overview، شمارش پروفایل‌ها، ذخیرهٔ Maintenance و Audit Log اضافه شده است. این مرحله هنوز E2E روی Firebase واقعی/cPanel تست نشده و نقش Owner اولیه باید فقط از Firebase Console یا Backend مورد اعتماد bootstrap شود. مدیریت Gemini/Shop/Users/Deploy هنوز پیاده‌سازی نشده است.


- [ ] مسیر و ظاهر مستقل `/admin` یا تب اختصاصی «مدیریت سایت»، **فقط برای مدیر اصلی تأییدشده**؛ مطابق تم و زبان اپ در دسکتاپ و موبایل. پنل برای کاربر عادی حتی با دست‌کاری URL قابل استفاده نباشد.
- [ ] تعریف نقش‌ها و اختیارات از سمت سرور: `owner`، در صورت نیاز `admin/moderator` و `user`. تعیین/حذف نقش مدیر از رابط کاربری عمومی یا با فیلد قابل‌نوشتن در Firestore ممنوع؛ استفاده از Firebase Auth Custom Claims یا سامانهٔ نقش قابل اعتماد با تنظیم اولیهٔ امن مالک و بررسی مجوز در **تمام درخواست‌های بک‌اند و Security Rules**. صرف مخفی‌کردن دکمه، درج ایمیل ثابت در JS یا شرط کلاینتی کافی نیست. برای عملیات حساس تأیید دوبارهٔ هویت و ثبت گزارش ممیزی لازم است.
- [ ] داشبورد کنترل کلی: آمار واقعی کاربران، ثبت‌نام‌ها، استفادهٔ برنامه، خطاها، سلامت سرویس و هزینه/سهمیهٔ API با محدودهٔ زمانی؛ عدم نمایش آمار مصنوعی یا اطلاعات خصوصی افراد به‌طور پیش‌فرض.
- [ ] مدیریت کاربران و اجتماع با دسترسی متناسب: جست‌وجوی حساب‌ها، وضعیت حساب/نقش، رسیدگی به گزارش تخلف، محدودسازی/رفع محدودیت، مدیریت درخواست‌های پشتیبانی، حذف/بازیابی مجاز داده‌ها طبق خط‌مشی، تنظیم نمایش پروفایل و فید. دسترسی به محتوای خصوصی تسک‌ها، ژورنال و دردودل «آزادی» صرفاً برای مدیر **به‌صورت پیش‌فرض وجود نداشته باشد**؛ سیاست روشن، حداقل دسترسی، رضایت/مجوز قانونی و ثبت دسترسی ضروری است.
- [ ] مدیریت تنظیمات سراسری سایت: روشن/خاموش‌کردن قابلیت‌ها، محدودیت استفاده، زبان‌ها و تم‌های قابل انتخاب، قوانین XP/لول/لقب/مدال، مأموریت‌ها، بنرها و اعلان‌های عمومی، قواعد چالش/رنکینگ، پشتیبان‌گیری و نمایش سلامت انتشار. تنظیمات معتبرسازی‌شده و نسخه‌بندی شوند؛ تغییرات مخرب نیازمند تأیید و امکان بازگردانی باشند.
- [ ] گزارش ممیزی اقدامات ادمین (چه کسی، چه کاری، چه زمانی، نتیجه) با حفاظت از اطلاعات حساس؛ کنترل نرخ، مدیریت خطا، آزمون نفوذ در سطح دسترسی، آزمون نقش کاربر عادی در برابر مدیر و آزمون دو حساب مستقل.

## ۲. مدیریت چند کلید Gemini و انتخاب مدل از پنل مدیر

- [ ] صفحهٔ «هوش مصنوعی / Gemini» در پنل مدیر برای افزودن **چند کلید API** با نام مستعار، وضعیت فعال/غیرفعال، اولویت، برچسب محیط، زمان آخرین استفاده، محدودیت مصرف و حذف/تعویض (rotation) امن؛ نشان‌دادن فقط بخش ماسک‌شدهٔ کلید، بدون امکان خواندن دوبارهٔ متن کامل آن از رابط کاربری یا گزارش‌ها.
- [ ] کلیدها **هرگز** در GitHub، فایل ZIP، `index.html`، JavaScript مرورگر، `localStorage`، Firestore قابل خواندن توسط کاربر، پیام خطا یا لاگ عمومی قرار نگیرند. دریافت و نگه‌داری از طریق بک‌اند دارای کنترل دسترسی و مخزن اسرار مناسب؛ فراخوانی Gemini صرفاً از بک‌اند پس از احراز هویت و اعمال سهمیه/هزینه انجام شود. برای اجرا، نیازمندی‌های هاست و پلن Firebase/Spark یا سرویس جایگزین و قیمت/سهمیهٔ روز را پیش از پیاده‌سازی بررسی کنید؛ **رایگان‌بودن Firebase به معنی رایگان‌بودن استفادهٔ نامحدود Gemini نیست**.
- [ ] ثبت **فهرست مدل‌ها** با شناسهٔ دقیق و معتبر مدل (نه نام نمایشیِ ساختگی)، فعال/غیرفعال، مدل پیش‌فرض، مدل جایگزین، اولویت مدل و نگاشت مدل به هر قابلیت؛ برای مثال «آزادی: گفت‌وگو/اولویت‌بندی/تبدیل پیشنهاد به تسک». مدل‌های در دسترس، سازگاری، سقف طول ورودی/خروجی، هزینه و تغییرات نسخه در زمان اجرا از مستندات/سرویس رسمی کنترل شوند. مدل دلخواه مدیر فقط پس از صحت‌سنجی قابلیت و مجوز ذخیره شود.
- [ ] منطق مدیریت چند کلید: انتخاب بر اساس اولویت/سهمیه و سلامت، failover **فقط** برای خطاهای قابل تلاش مجدد، backoff و سقف دفعات، جلوگیری از پاسخ تکراری/هزینهٔ مضاعف، جداسازی سهمیهٔ کاربران و قابلیت‌ها؛ دورزدن محدودیت‌های ارائه‌دهنده یا چند برابرکردن مصنوعی سهمیه با کلیدهای متعدد مجاز فرض نشود.
- [ ] داشبورد مصرف، تعداد درخواست/خطا، برآورد هزینه و بودجهٔ روزانه/ماهانه، محدودیت هر کاربر، هشدار رسیدن به سقف، قطع اضطراری AI، تاریخچهٔ تغییر تنظیمات؛ داده‌های حساس مکالمات در لاگ تحلیل/مصرف ذخیره نشوند.
- [ ] «آزادی» در وضعیت فعلی **فقط یک تب آماده است و AI واقعی هنوز متصل نشده**. در نسخهٔ آینده، متن نگرانی‌ها فقط با رضایت کاربر به مدل فرستاده شود؛ اولویت‌ها و تسک‌های پیشنهادی ابتدا به کاربر نمایش داده شوند و **فقط پس از تأیید صریح او** وارد برنامه شوند. حریم خصوصی، حذف مکالمه/داده، خطاها و هزینه‌ها روشن باشند؛ پاسخ ثابت را به‌جای هوش مصنوعی واقعی نمایش ندهید.

## معیار پذیرش و ترتیب اجرا

۱. ابتدا گام صفر رودمپ اصلی، امنیت Firebase و آزمون دو حساب تثبیت شود؛ سپس زیرساخت نقش مدیر و بک‌اند امن و فقط بعد از آن فرم کلید/مدل فعال گردد. ۲. تست منفی ثابت کند کاربر عادی نمی‌تواند از URL مستقیم، DevTools، API یا ویرایش Firestore به پنل، کلیدها یا تنظیمات مدیریتی دسترسی پیدا کند. ۳. کلید واقعی در ZIP، فایل‌های فرانت‌اند و لاگ‌ها حضور نداشته باشد؛ هزینه و سهمیه محدود شده باشند. ۴. مدل پیش‌فرض و fallback در پنل قابل تغییر و نتیجهٔ تست اتصال/خطای آن روشن باشد. ۵. ابتدا روی حساب‌های آزمایشی و محیط جدا تست، سپس با تأیید مالک روی سایت منتشر شود.

**سؤالات باز برای جمع‌آوری ایده‌ها:** دامنهٔ اختیارات مدیر (مثلاً نوع نظارت بر فعالیت‌ها و حذف حساب)، نقش‌های کمکی، مدل‌های مشخص، بودجه و روش میزبانی بک‌اند هنوز از طرف آرن نهایی نشده‌اند؛ در طول گفتگو به‌روزرسانی شوند و بدون دادهٔ کافی مقدار حدسی ثبت نگردد.


## ۳. هویت نمایشی Elara و نام مدل

- [ ] در UI نام دستیار و نام نمایشی مدل می‌تواند مستقل از شناسهٔ فنی Provider/Model باشد؛ برای مثال کاربر «Elara» را ببیند و شناسهٔ واقعی فقط در پنل مدیر/لاگ امن نگه‌داری شود.
- [ ] Prompt و Policy چندزبانه برای حفظ شخصیت Elara، جلوگیری از افشای API key، system prompt، secret و جزئیات داخلی زیرساخت.
- [ ] مدل نباید داوطلبانه جزئیات فنی غیرضروری را در تجربهٔ روزمره نمایش دهد؛ **اما اگر کاربر مستقیماً دربارهٔ فناوری زیربنایی سؤال کرد، پاسخ نباید به‌دروغ ادعا کند مدل پایه توسط Elara ساخته شده است.**
- [ ] Display name، provider، technical model id، default/fallback و قابلیت‌های مجاز هر مدل فیلدهای جدا باشند.

## ۴. AI Verification برای گزارش‌های رقابتی

- [ ] AI check فقط برای فعالیت‌های رقابتی/Verified و در صورت نیاز اجرا شود؛ گزارش‌های عادی کاربر آزاد باقی بمانند.
- [ ] Reading report: بازهٔ صفحات + توضیح کاربر + سؤال follow-up برای سنجش درک مطلب؛ در صورت داشتن متن قانونی/فایل خصوصی، سؤال از همان محدوده ساخته شود.
- [ ] خروجی ساختاریافته شامل `confidence`، `reasons`، `follow_up` و نتیجهٔ قابل استفاده برای Verified Points باشد؛ خروجی AI **اثبات قطعی تقلب یا مطالعه نیست**.
- [ ] Workout report: نوع، مدت، جزئیات تمرین و در صورت امکان دادهٔ تایمر/Integration؛ Focus challenge فقط از تایمر خود Elara امتیاز معتبر بگیرد.
- [ ] سطح اعتماد Activityها به‌صورت `self_reported` / `app_tracked` / `ai_checked` / `integrated` ثبت شود و قوانین Challenge مشخص کنند کدام سطح معتبر است.
- [ ] Random spot-check، rate limit، سقف هزینه و جلوگیری از پرسش‌های تکراری/قابل حفظ شدن.
- [ ] نتیجهٔ Challenge و XP/Rank رقابتی در سمت سرور ثبت شود؛ کاربر یا Owner Club نتواند آن را دستی تغییر دهد.
